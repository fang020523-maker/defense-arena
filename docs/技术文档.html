一、作品概述

1.1 痛点定义

每年全国有超过百万研究生与本科生参加学位论文答辩。答辩前的模拟练习存在三个真实痛点：

  • 没有对手：学生只能"对着空气练习"，缺乏真实的高压质询环境；
  • 导师资源稀缺：导师不可能反复陪练，模拟答辩组织的成本高；
  • 反馈不结构化：真人练习后的意见碎片化，难以沉淀为可执行的改进清单。

1.2 解决方案

「赛博答辩厅」把答辩委员会搬进浏览器，构建一条 论文 → 检索锚定 → 多智能体对抗 → 结构化反馈 的完整产品闭环：

环节体验技术支撑
① 备战拖入论文 PDF（全程本地解析，隐私零上传）pdf.js 文本抽取 + 分块 + BM25 索引
② 开场AI 答辩人基于论文生成 5 分钟开场陈述（或使用用户自带稿）检索 Top-5 片段注入 + 流式生成
③ 质询4 位评委轮流提问，AI 答辩人即时作答；画布实时展示消息流多智能体编排状态机 + SSE 流式
④ 追问⚡压力模式：评委更尖锐，末轮针对此前回答连环追问答辩记录压缩 + 条件分支 Prompt
⑤ 评分每位评委独立五维打分（选题/创新/方法/表达/工作量）DeepSeek JSON 模式 + 校验回填
⑥ 终评主席输出结构化 Markdown 报告，可导出 .md聚合评审上下文生成

二、意图控制策略（Prompt 工程）

本作品的核心竞争力在于"驾驭 AI 智能体"的方法论。以下四个意图控制手段贯穿全部生成环节：

2.1 幻觉约束——检索锚定

多智能体评审类应用最大的质量风险是评委"凭空编造论文内容"。我们的解法是把 RAG 作为人设的一部分写进 System Prompt 纪律条款：

# 提问纪律（必须严格遵守）
1. **锚定真实**：你的问题必须建立在提供的「论文摘录」之上，
   严禁编造论文中不存在的内容或数据。
2. **一次一问**：每次只提出一个问题，具体、可回答，长度 2-4 句，
   不给答辩人逃答空间。
3. **禁止重复**：参考「答辩记录」，不得重复任何已问过的问题。
4. **联动深挖**：若答辩记录中其他评委的提问或答辩人的回答暴露了
   新疑点，优先顺势深挖。
5. **直入主题**：不要过渡语，不要客套。
6. **压力模式已开启**：你的提问应当尖锐、连环、不留情面……

每次评委发言前，引擎以「评委关注维度 + 论文标题」（或追问场景下的「前问 + 前答」）为查询串，检索 Top-4 论文片段注入用户消息，形成 「人设纪律 × 真实证据」双重约束。答辩人的 System Prompt 同理：忠于论文、坦诚边界、结论先行。

2.2 差异化人设——正交评审维度

四位评委刻意覆盖四个不重叠的评审维度，避免多智能体"同质化发言"：

评委人格原型正交维度典型切入
🔬 严正声（严博导）方法论手术刀方法严谨基线对照、样本量、统计显著性、逻辑跳跃
📖 温文澜（温和教授）轻柔但极深表达理解用自己的话解释概念、研究动机、创新点陈述
🏭 石力行（行业专家）务实反黑话落地价值解决谁的什么问题、部署成本、工业界对比
🚀 芮敏（青年学者）顶会雷达前沿创新SOTA 对标、增量 vs 突破、相关工作遗漏

2.3 上下文工程——记录压缩

答辩到后期，完整记录会超出合理的上下文预算。我们实现了 保头保尾的滑动窗口压缩：保留开场两条 + 从最新往回回填直至 2.8K 字符预算，中间以省略号衔接。这样既保住了"联动深挖"所需的最新信息，又保留了开场的全局语境。评分与终评环节预算放宽至 3.6K/4.2K。

2.4 结构化输出——JSON 模式双保险

评分环节启用 DeepSeek response_format: {type:'json_object'}（服务端白名单放行），前端再以三重防御解析：剥离 Markdown 代码块包裹 → indexOf('{')…lastIndexOf('}') 截取 → 五维数值校验（缺失维度以有效分均值回填，全缺则重试），保证渲染层永远拿到合法的 DimScores。

四、关键技术实现

4.1 轻量 RAG：为什么 BM25 就够了

单篇论文的分块规模通常在 50–150 块。在这个量级上，BM25 的检索质量与向量检索差距极小，而工程收益显著：无需 Embedding API（DeepSeek 亦不提供）、无需外部向量库、索引构建在毫秒级。分词器针对中英混排设计：中文按二元词组（bigram）（规避中文分词依赖），英文按词级 + 停用词过滤；BM25 参数取 k1=1.5、b=0.75。

4.2 分块策略：段落聚合 + 重叠窗口

以 600 字为目标块长、80 字重叠：先按换行切段落，段落聚合逼近目标长度；对无换行的超长段落（整页连排）回退为定长窗口硬切；相邻块保留尾部重叠以维护跨块语义连续；小于 100 字的尾块并入前块。每块携带页码，为后续"引用溯源"预留能力。

4.3 流式体验工程

  • 节流写入：SSE token 级回调以 90ms 节流刷新 store，避免高频重渲染拖慢画布动画；
  • 状态编排：节点状态机 idle → thinking → speaking → done，边高亮跟随 activeEdge（质询=评委色发光边，答辩=青色回流）；
  • 思维链可视化：兼容 deepseek-reasoner 的 reasoning_content，评委"深度思考"状态在节点上呈现。

五、可复现性论证

  • 十分钟复现：README 提供四步指南（克隆安装 → npm run dev → 填 Key → 跑答辩），仓库自带示例论文 public/sample-paper.pdf，评委无需自备材料即可体验完整闭环；
  • Prompt 演进链：PROMPT_LOG.md 记录 5 条核心迭代链（意图 → 实现 → Bug 引导修复 → Git 提交对应），本作品开发中真实发生的编译错误（pdfjs v6 API 变更、TS 严格模式、类型宽度推断）及其修复过程均如实记录；
  • 细粒度提交：Git 历史按功能模块逐次提交（脚手架 → 代理服务 → RAG → 引擎 → 画布 → 向导/报告 → 文档），每次提交对应一个可独立验证的功能增量，无"一次性 initial commit"；
  • 零私有依赖：唯一外部服务是 DeepSeek API，任何评委注册即可复现，无付费墙。

六、工程质量与安全

  • 类型安全：TypeScript strict 模式（noUnusedLocals / erasableSyntaxOnly / verbatimModuleSyntax），tsc -b 零错误；
  • 构建验证：npm run build 生产构建通过；Express 生产模式托管静态资源，单进程部署；
  • 隐私设计：论文解析全程浏览器本地完成，只有检索命中的片段（每问约 2.4K 字符）发送给模型用于生成；
  • 错误体验：上游 401/402/429/超时均翻译为中文提示；Key 无效/余额不足/限流分别引导。

八、总结

「赛博答辩厅」用 Vibe Coding 范式在极短周期内交付了一个痛点真实、闭环完整、演示炸裂的多智能体应用：人类专注于定义问题（选题决策、意图描述、验收引导），AI 承担全部代码生产。全部开发过程通过 PROMPT_LOG 与细粒度 Git 历史留痕，可复现、可审计——这本身就是对"意图驱动编程"这一赛题主旨的最佳注解。
